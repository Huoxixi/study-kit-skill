S01|长上下文、标度规律与涌现|model|三项研究分别讨论位置、训练规模和评价现象。|Lost in the Middle 研究部分模型利用长上下文中不同位置的信息；Chinchilla 研究给定训练算力下参数量与训练 token 的配置；涌现研究指出，一些表面突跃与不连续指标有关。三者不是同一个结论。|让同一模型查一份很长的班级通知，分别把集合时间放在开头、中间、结尾，再比较回答。这个测试只检查这份材料和这个模型，不能推到所有模型。|上下文位置利用弱不等于内容一定被截断；特定研究不能当作所有当前模型的永久规律。|上下文窗口足够大就能保证每个位置的证据都被同样准确利用。
S02|API 请求、鉴权与错误处理|model|API 是应用程序编程接口。|API 是程序接口的一种通称；本卡讨论 HTTP 接口。请求包括地址、方法、请求头及可选请求体，响应包括状态码与内容。400 表示服务器认为请求有语法、格式等问题；401 表示缺少有效认证凭据；429 表示一段时间内请求过多。字段和限额以具体接口为准。|天气软件向服务发出“查上海明天天气”的请求，再把返回内容显示出来。像去窗口办事，请求要说清办什么，所需凭据也得有效。|不能把所有错误都当作参数格式错；密钥不要贴进截图，重试也不能无限进行。|HTTP 401 通常意味着请求参数格式有误，与认证无关。
S03|参数高效微调 PEFT|model|PEFT 只调整或引入较少可训练参数。|参数高效微调 PEFT 减少需要更新的参数。LoRA 冻结基础权重，学习低秩权重增量；Prefix Tuning 学习连续前缀表示；P-Tuning v2 使用深层提示方法。这些方法与全参数微调不同。|想让模型把活动通知写成固定格式，可以用示范训练一小部分新增参数。像给已有工具加一个专用配件，但实际学的是参数，不是贴一句提示就结束。|参数少不等于不用数据，也不保证质量超过全参数微调。|LoRA、Prefix Tuning 和 P-Tuning v2 都是常见参数高效适配思路。
S04|文档切分与上下文保留|rag|文档切分把长资料分成可检索的片段。|切分可按固定长度、标题、段落或语义边界进行。重叠使相邻片段共享部分内容；元数据保留标题、页码和版本等。片段大小与重叠需要结合文档结构和检索结果选择。|一份学校通知分为“报名、考试、查成绩”。问报名截止日期时，先找报名段；别把“截止日期”切在一块、适用条件切到另一块，导致看半句就答错。|不是所有文档都适合同一长度或重叠比例；表头、单位和条件不能随意丢掉。|所有文档都应该使用完全相同且不经验证的切片重叠比例。
S05|Embedding、度量与元数据|rag|Embedding 把对象映射为向量表示。|嵌入模型将文本等对象编码为向量；检索用匹配的表示和度量比较接近程度。余弦相似度比较夹角；非零向量归一化为单位长度后，其内积等于余弦相似度。元数据可另外用于过滤。|搜“手机没电了怎么办”时，向量检索可能找到“如何给手机充电”。词不完全相同，但语义可能接近；若只想看本校通知，还得加资料范围条件。|不能混用不匹配的嵌入模型或任意截断维度；也不是每种度量都要求手动归一化。|对非零查询向量和文档向量都做单位长度归一化后，内积等于余弦相似度。
S06|检索元数据与权限过滤|rag|元数据过滤限制可进入检索的资料范围。|元数据是描述资料的信息，如部门、文档类型、发布日期和访问控制信息。过滤根据条件保留候选；访问控制则由服务端根据身份强制执行，不能由用户在问题里自报身份来决定。|同学查课表只能查学生可看的资料，老师内部会议记录即使内容相关，也不能一起返回。像图书馆里能搜到书名，不代表能打开任何受限文件。|只在提示词里写“不要泄密”不能实现权限控制；未经授权的片段也不应先送给模型再遮掉。|只在提示词写“不要泄密”就足以实现多租户数据隔离。
S07|混合检索与结果融合|rag|混合检索结合关键词与向量等检索方式。|关键词检索按词项匹配，向量检索按表示的接近程度匹配。混合检索合并两类结果；RRF 等方法根据排名融合，评分融合则需要处理不同分数尺度。|查“G123 次列车”，准确车次很重要，关键词有用；查“能放折叠伞的小包”，描述可能有多种写法，语义检索也有用。|BM25 分数和向量分数不在同一尺度，不能不加说明就直接相加。|BM25 分数和向量相似度无需处理就总能直接等权相加。
S08|重排序与检索评估|rag|重排序对已召回的候选重新评估相关性。|重排序对查询和已召回候选重新评分或排序。Recall@K 是前 K 条找回的相关资料数占全部已知相关资料数的比例；单次查询 RR 是首个相关结果排名的倒数，MRR 是多次查询 RR 的均值；nDCG 综合相关程度与位置，并相对理想排序归一化。|找“报名截止时间”，先搜出几十段，再把真正写截止时间的段落排前。若首个相关结果在第 2 位，这次 RR=1/2；多个问题的 RR 平均才是 MRR。最初完全没召回的资料，重排不能凭空补回。|检索指标和回答是否忠实是两件事；排序靠前的资料仍可能过期或没有访问权限。|重排序可以直接找回所有在召回阶段完全遗漏的文档。
S09|KV Cache 与 PagedAttention|serving|KV Cache 保存已处理 token 的键和值。|自回归注意力可缓存先前 token 在各层产生的 K、V 张量，避免每步重复计算。PagedAttention 用块及映射管理这些缓存，减少连续预留带来的空间浪费，并支持共享等机制。|聊天助手生成一段回复时，后续 token 要参考前文。前文已算出的 K、V 张量可以缓存，后续不必重算这些张量，但仍要进行新的查询和注意力计算。这不是把前文压成摘要，也不是缓存整段答案。|KV Cache 和保存“这个问题上次答什么”的语义缓存不同；缓存仍会占显存。|KV Cache 与缓存整个问答结果的语义缓存是同一个东西。
S10|批处理与请求调度|serving|批处理把多个请求放在一起计算。|静态批处理固定一批请求；连续批处理可在生成迭代之间加入或移除请求。调度决定处理顺序，如先来先服务或按优先级；抢占会涉及状态保存或重算等成本。|聊天助手同时处理几个人的请求，有人只要一句话，有人要长回复。短回复结束后，后续解码轮次可加入新请求，不必等长回复全部结束。这是在计算迭代之间调度，不是把独立回复拼成一段。|优先级没有防饥饿措施时，普通请求可能一直排不上；批量大也不保证每人等待短。|优先级调度如果没有防饥饿设计，可能让低优先级请求长期等待。
S11|投机解码|serving|投机解码由草稿提出候选，目标模型验证。|投机解码先用较便宜的方法提出多个候选 token，再由目标模型验证并接受其中符合规则的部分。采用相应精确算法时可保持目标输出分布；加速效果取决于接受率、草稿成本和运行负载。|聊天助手续写一段短消息时，草稿方法先提出几个候选 token，目标模型再批量验证。若中间候选未通过，就按算法的接受与校正规则继续；不是用户觉得句子顺眼就算通过，也不保证草稿全被接受。|草稿经常被拒绝或验证开销太大时，可能没有加速，甚至更慢。|投机解码在任何负载与任何草稿接受率下都一定加速。
S12|TTFT、TPOT 与吞吐|serving|TTFT、TPOT 和吞吐衡量不同方面。|同一测量端点下，TTFT 是请求开始至首 token 的时间。输出 N>1 个 token 时，TPOT=(完成时间−首 token 时间)/(N−1)。N≤1 时无后续间隔，需注明统计约定，vLLM 可记录为 0；ITL 是相邻流式输出的间隔，多 token 一次发出时不等于单 token 耗时。吞吐按单位时间的请求或 token 数计。|假设聊天请求在 0 秒开始，2 秒收到首 token，3.8 秒全部完成，共输出 10 个 token：TTFT=2 秒，TPOT=(3.8−2)/(10−1)=0.2 秒/token。这里数的是 token，不是汉字；换测量端点或按网络分块计时，数值口径也可能不同。|TPOT 用 ms/token 表示时越小通常越快；总吞吐提高，不代表每人的首 token 都更快。|TPOT 以 ms/token 计量时，数值越高表示生成越快。
S13|语义缓存与模型路由|serving|语义缓存复用近似问题的结果，路由选择处理方式。|语义缓存按向量等相似性查找可复用结果；模型路由按任务和策略选择模型或其他处理路径。复用需同时满足资料版本、权限和关键条件，不能只比较问题写法。|昨天有人问“图书馆几点关门”，今天闭馆时间变了，昨天的答案就不能直接复用。两个问法很像，也不代表条件没变。|语义相似不等于答案可复用；不得向无权用户复用含私有信息的结果。即使共同有权访问，也要核对版本和问题条件。|只凭语义相似就可以跨租户复用包含私有信息的答案。
S14|推理框架选型|serving|推理框架提供模型运行和服务能力。|vLLM、TGI、SGLang 和 TensorRT-LLM 都有各自的模型服务与优化支持；支持范围依模型、硬件和版本变化。选型应比较需要的功能与同条件测试结果，不能按名称推断固定性能排名。|在同一台电脑上，用同一模型、同一批问题，固定精度、并发和生成长度等设置，再比较不同框架。只固定问题长度，却换了模型、精度或负载，就不能把速度差全归给框架。|本项目未对这些框架做性能实测；TGI 等项目维护状态也需按所用版本检查。|只根据框架名称就能确定它在任何硬件和负载下最快。
S15|多租户端到端隔离|ethics|多租户隔离限制不同用户组的数据访问。|租户是系统中需隔离的一组用户和资源。服务端验证身份并确定权限，在检索、缓存、工具、日志及输出等环节保持边界；隔离可采用物理分离或适当的逻辑访问控制。|假设两所学校是平台的两个租户，甲校账号不能因为在问题里写“我是乙校老师”，就读到乙校内部文件。老师、学生也可能是同一租户中的不同角色，角色和租户不能混用。|身份与权限由可信系统确认，不能由用户提示词直接决定。|用户在提示词中自称属于某部门就应自动获得该部门资料权限。
S16|脱敏、追踪与审计|ethics|脱敏减少敏感暴露，审计记录必要的访问活动。|脱敏按任务遮蔽、替换或移除敏感信息；审计记录谁在何时访问或操作了什么，以便检查和追溯。日志本身也需要访问控制、保留期限和必要性限制。|把快递单照片发到群里前，遮住姓名、电话和住址，是常见的脱敏。系统记录谁查看了原图，则属于访问审计。|快递单还可能通过地址、电话或条码关联本人，遮名不等于不可重新识别。磁盘加密也不等于控制解密后的内容由谁读取，仍需权限、适当脱敏和审计。|只要磁盘加密，就不需要脱敏、权限管理或安全审计。
S17|Function Calling、ReAct 与终止条件|agent|工具调用把模型请求交给外部程序执行。|工具定义说明名称、用途和参数结构。模型提出调用，服务端校验权限与参数后执行，并将结果返回。ReAct 将推理与行动、观察交替组织；执行系统还应设置完成、失败、超时或步数等终止条件。|问“明天出门带伞吗”，助手调用天气工具，读到结果后再回答。工具连续报错时，应停下说明情况，不能一直查下去。|模型说“调用工具”不代表已执行成功；参数由模型生成也仍要检查。|Function Calling 的参数只要由模型生成，就无需服务端校验。
S18|OCR、VLM 与多模态证据|rag|OCR 识别文字，VLM 联合处理视觉与语言。|OCR 将图像中的文字转换为可处理的字符；视觉语言模型 VLM 联合图像与语言进行理解或生成。图表理解还涉及布局、坐标和数值关系，应保留原图区域以便核对。|把超市小票拍照后转成文字，可用 OCR；问手机步数折线图“哪天最多”，还得看横轴日期、纵轴数量和折线位置。|OCR 和 VLM 都会出错；读图表不能只看趋势而忽略单位或负号。|图表解读时应核对坐标、单位、数值和来源区域。
S19|AI Coding 工具与规则|agent|编程助手、连接协议和项目规则用途不同。|编程助手可辅助生成、解释和修改代码；MCP 是连接模型应用与外部工具、数据的开放协议；AGENTS.md 是向编程代理传达项目要求的一种文件约定。它们不是同一类产品。|让编程助手给购物清单加一个“合计”按钮；项目规则写着“金额保留两位小数”，它应据此修改。真正能否读取文件，还取决于系统权限。|规则文件不能替代操作系统权限和服务端鉴权；协议本身也不是完整编程助手。|项目规则文件能够替代系统级文件权限和服务端鉴权。
S20|Gradio 聊天界面|agent|ChatInterface 是 Gradio 的高层聊天界面封装。|Gradio ChatInterface 围绕聊天函数组织输入、历史和输出，减少手工搭建聊天界面的工作。具体参数与消息格式需按使用版本确认；已核对源码中该类继承 Blocks。|给一个简单的课程答疑函数配上输入框和聊天记录区，可以用 ChatInterface。界面负责交互，函数仍要处理问题和返回内容。|样题把它称为 Interface 的“特殊变体”是宽泛表述，不应当作严格的 Python 继承关系。|Gradio 的聊天界面封装能够减少手工组织常见对话 UI 的工作。
